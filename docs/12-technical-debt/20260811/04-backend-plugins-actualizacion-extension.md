# Auditoría — Actualización de Plugins, Rollback, Extensiones y Configuración

**Subsistema:** Plugin Update / Extension / Config
**EPIC cubiertas:** EPIC 6 (plugins tipo extension), EPIC 7 (actualizaciones de plugins y rollback)
**Severidades:** 1 crítico · 4 mayor · 5 menor · 1 nit

Índice: [Auditoría consolidada](00-informe-consolidado.md)

Alcance revisado en profundidad (lectura completa, no solo grep): los 10 ficheros de `backend/src/plugins/application/`, controladores y repositorios de plugins/configuración, migraciones 006/007, plugins `comments` y `demoinventory` completos (incluyendo `plugin.js` y versiones v1/v2), toda la suite de tests indicada, y los docs de referencia. También se leyó de apoyo `PluginSourceService`, `PluginSchemaReader`, `PluginSchemaCodec`, `PluginCompatibilityValidator`, `PluginManifestReader`, `PluginDependencyValidator` y `PluginLifecycleInvoker`.

## Hallazgos por severidad

### CRÍTICO

**1. El diff "solo aditivo" confunde el catálogo de diseño (`schema.json`) con el estado runtime configurado (`plugins.schema_json`), y esto puede bloquear permanentemente las actualizaciones o forzar la activación silenciosa de campos no solicitados.**
- Ficheros: `backend/src/plugins/application/PluginSchemaMergeService.php:64-70,143-176`, `InstalledPluginSchemaValidator.php:134-165`, `PluginAdministrationService.php:161-164` (en `saveConfig`).
- Categoría: bug de correctitud / diseño de datos.
- El diseño documentado en `decisiones-tecnicas.md` (DECISION 5) dice que `custom_fields` es un "catálogo de sugerencias opcionales" que el admin puede activar/editar. Al llamar a `saveConfig()`, `PluginAdministrationService` reescribe `plugins.schema_json.custom_fields` para que pase a significar **campos activos** (no ya "catálogo"), y mueve el catálogo real a una clave nueva, `plugin_suggested_custom_fields` (línea 162). El problema es que `PluginSchemaMergeService::mergeAdditively()` y `InstalledPluginSchemaValidator` **no conocen `plugin_suggested_custom_fields`**; siguen tratando la clave `custom_fields` persistida como si fuera el catálogo canónico del plugin.
  - Consecuencia A (bloqueo falso positivo): si el admin edita el `label` o `type` de un campo sugerido ya activo (acción explícitamente permitida por `compileEntityConfigRows`, que solo protege los campos *base*, no los sugeridos), la próxima llamada a `update()` invoca `assertOverlappingListDefinitionsMatch()` (`InstalledPluginSchemaValidator.php:152-164`), que compara ese campo editado contra la definición original de `schema.json` y lanza `DomainException("... custom_fields.X changed.")`. El plugin queda **permanentemente bloqueado para futuras actualizaciones** aunque el `schema.json` en disco no haya cambiado en absoluto para ese campo.
  - Consecuencia B (activación forzada sin consentimiento): si una nueva versión del plugin añade un campo sugerido nuevo (p. ej. `stock` en `demoinventory` v2), `mergeListSectionByKey` lo añade directamente al array `custom_fields` persistido. Si el plugin ya fue configurado antes, ese array ya no es "catálogo" sino "activos" — el campo nuevo aparece automáticamente **activo** para el usuario final, sin pasar nunca por `plugin_suggested_custom_fields` (por lo que ni siquiera aparecerá como opción togglable en la UI de configuración, ya que `suggestedCatalogFromSchema()` solo cae al fallback de `custom_fields` cuando `plugin_suggested_custom_fields` no existe).
- Por qué importa: rompe justo la promesa central de EPIC 7 ("actualización segura, solo aditiva") en el camino de uso más realista (configurar → actualizar), y no está cubierto por ningún test — todos los tests de `PluginUpdateServiceTest.php` usan esquemas nunca pasados por `saveConfig()`.
- Sugerencia: la validación/merge de `custom_fields` debería comparar siempre contra `plugin_suggested_custom_fields` (el catálogo canónico), no contra la lista de "activos"; y los campos nuevos del `schema.json` deberían mezclarse en el catálogo de sugerencias, no en la lista de activos.

### MAYOR

**2. Las actualizaciones de plugins `extension` no aplican ningún diff de schema — la ampliación de STORY 7.3 a extensiones no se propagó a STORY 7.2.**
- Ficheros: `PluginUpdateService.php:67-74`, `PluginSyncService.php:100-106`.
- El backlog (`docs/11-backlog/backlog.md:820-852`, "Refuerzo STORY 7.3") extiende explícitamente la **configuración** de plugins a `extension`, pero `PluginUpdateService::update()` solo llama a `assertCanApplyUpdate()`/`mergeAdditively()` cuando `manifest['type'] === 'entity'`. Para una `extension`, `$mergedSchema` queda igual a `$currentSchema`, `$schemaChanged` queda `false`, y `PluginRepository::persistUpdate()` nunca reescribe `schema_json`. Si el autor de una extensión (p. ej. `comments`) añade un campo nuevo a `schema.json` en una versión nueva, ese campo **nunca llega a las instalaciones existentes** vía `update()`; solo se aplicaría en una instalación nueva desde cero. Lo mismo ocurre con `PluginSyncService::syncSlug()`: la detección de "schema instalado corrupto" (`assertContainsCanonical`) también está condicionada a `type === 'entity'`, así que una extensión con esquema corrupto nunca se reporta como error en `syncAll()`.
- Por qué importa: es exactamente el patrón de "refactor incompleto" — la ampliación a `extension` quedó a medio camino, coherente en el panel de configuración pero no en el ciclo de actualización. Ningún test (`PluginUpdateServiceTest.php`) usa un fixture `type: 'extension'`.
- Sugerencia: extender `mergeAdditively`/`assertCanApplyUpdate` (que ya operan sobre `fields` como sección asociativa genérica) para cubrir también `extension`, o documentar explícitamente que las extensiones no soportan diff de schema en el MVP.

**3. `PUT` sobre un ítem de extensión reescribe `author_id` con el usuario que edita, y no existe control de propiedad (cualquier usuario autenticado con acceso a la entidad puede editar/borrar comentarios ajenos).**
- Ficheros: `backend/src/controllers/ExtensionPluginContentService.php:20-40,129-157` (en particular 137-146), `PluginExtensionController.php:97-125` (`update()`), `guardExtensionWriteRequest` en `346-369`.
- `normalizeContentBySchema()` se usa sin distinción para `create()` y `update()`. Para un campo `auto_generated` como `author_id` (`plugins/comments/schema.json:12-18`, `editable: false`), `resolveAutoGeneratedValue()` **siempre** recalcula el valor a partir del `sub` del JWT del solicitante actual (líneas 137-146), en cada `PUT`. Como `guardExtensionWriteRequest`/`guardExtensionRequest` solo verifican que el plugin esté activo, la entidad esté permitida y exista el registro padre —nunca que el solicitante sea el autor original—, cualquier usuario autenticado puede editar (y, de paso, reasignarse la autoría de) el comentario de otro usuario.
- Por qué importa: contradice la semántica de `editable: false` para un campo marcado como identidad de autoría, y es un hueco de autorización real, no solo cosmético. Confirmado por ausencia total de test: `CommentsPluginTest.php` no ejercita `update()` en ningún caso (solo GET/POST), así que el bug nunca se habría detectado por la suite existente.
- Sugerencia: distinguir explícitamente el contexto create/update en `normalizeContentBySchema` (no recalcular campos `auto_generated` en update salvo los que representen "última modificación", como `stamp`) y añadir verificación de propiedad (`author_id === request.user.sub`) antes de permitir editar/borrar, o documentar que es un modelo de confianza total entre usuarios autenticados (aceptable para MVP, pero debería ser una decisión explícita, no un efecto colateral).

**4. Falta de atomicidad inconsistente: `update()`/`rollback()` están correctamente protegidos con transacción, pero `syncAll()` (alta de plugin nuevo) y `activate()`/`deactivate()` no lo están.**
- Ficheros: `PluginSyncService.php:77-90` (`insert()` + `onInstall()` sin transacción), `PluginStatusService.php:22-47` (`updateStatus()` + `onActivate()`/`onDeactivate()` sin transacción). Contraste con `PluginUpdateService.php:44-113` y `PluginRollbackService.php:37-87`, que sí usan `beginTransaction()/commit()/rollBack()`.
- Si `Lifecycle::onInstall()` lanza una excepción (p. ej. un plugin que necesita crear su propia tabla y falla), la fila ya insertada en `plugins` por `PluginRepository::insert()` **queda comprometida** (no hay rollback posible porque nunca hubo transacción explícita). `syncSlug()` captura la excepción en el `try/catch` de `syncAll()` y simplemente la reporta como `result: error` en el resumen, pero el plugin queda registrado como si el alta hubiera sido parcialmente exitosa; en la siguiente sincronización ya no se re-intentará `onInstall()` (porque `existing !== null`), dejando el plugin en un estado "instalado pero mal inicializado" sin vía de recuperación automática. Mismo patrón en `activate()/deactivate()`.
- Por qué importa: el hallazgo relevante es que la disciplina transaccional (correcta y bien testeada en `update()`/`rollback()`, ver `PluginUpdateServiceTest.php` caso "rolls back plugin and snapshot when onUpdate fails") **no se aplicó uniformemente** al resto del ciclo de vida del mismo subsistema.
- Sugerencia: envolver `insert()+onInstall()` y `updateStatus()+onActivate/onDeactivate` en transacciones, igual que ya se hace en update/rollback.

**5. `PluginAdministrationService` no es una fachada limpia: concentra ~250 líneas de lógica de negocio de configuración de entidades y las comparte con `ExtensionPluginConfigService` inyectando sus propios métodos privados como *closures*.**
- Fichero: `PluginAdministrationService.php:115-172` (`saveConfig`) y `185-546` (toda la lógica de compilación de filas de configuración: `compileEntityConfigRows`, `buildEntityConfigPayload`, `baseFieldsFromSchema`, `suggestedCatalogFromSchema`, `orderedRows`, `normalizePayloadRows`, `normalizeFieldDefinition`).
- Para el camino `extension`, en vez de que `ExtensionPluginConfigService` reutilice un normalizador compartido, `PluginAdministrationService` le pasa sus propios métodos privados como callables: `fn(array $rows): array => $this->normalizePayloadRows($rows)` (línea 130), y en `buildConfigResponse` (líneas 304-309) `fn(array $entry): array => $this->normalizeFieldDefinition($entry)` y `fn(array $rowsByKey, array $schemaValue): array => $this->orderedRows($rowsByKey, $schemaValue)`.
- Por qué importa: es la evidencia más clara de solapamiento de responsabilidades entre los 10 ficheros (ver valoración específica más abajo). Este patrón de "inyección de callbacks" en vez de extraer un colaborador común (p. ej. un `FieldDefinitionNormalizer` reutilizado por ambos servicios) es sobre-ingeniería innecesaria para el alcance de un TFM y, a la vez, síntoma de una responsabilidad mal ubicada: la mitad más grande de la lógica de "configuración de campos de entidad" vive dentro de lo que debería ser un simple orquestador/fachada.
- Sugerencia: extraer un `PluginFieldNormalizer`/`EntityConfigRowBuilder` reutilizable por `PluginAdministrationService` (para entity) y `ExtensionPluginConfigService` (para extension), eliminando el paso de closures.

### MENOR

**6. Código duplicado literal: `ensureInstalledTypeMatchesManifest()` está copiado (mismo cuerpo) en dos servicios distintos.**
- Ficheros: `PluginSyncService.php:128-136` y `PluginUpdateService.php:120-128`.
- Misma lógica exacta (comparar `plugin_type` instalado vs `manifest['type']` y lanzar `DomainException`), duplicada palabra por palabra salvo el nombre del parámetro. Debería vivir en un único sitio (p. ej. `PluginSourceService` o un pequeño `PluginTypeGuard`) e inyectarse/reutilizarse.

**7. Lógica de normalización de comparación de esquemas duplicada entre dos clases hermanas.**
- Ficheros: `PluginSchemaMergeService.php:217-233` (`normalizeForComparison`) e `InstalledPluginSchemaValidator.php:213-229` (método idéntico), más `indexByKey`/`itemKey` en `PluginSchemaMergeService` vs `indexListSection` en `InstalledPluginSchemaValidator` (mismo propósito: indexar listas por `key`, implementado dos veces con ligeras variaciones). Dado que ambas clases ya colaboran en el mismo flujo (`PluginUpdateService`), sería más limpio extraer un pequeño `SchemaComparisonUtil` compartido.

**8. La normalización de `fields` (lista vs. objeto, `name`/`key` como alias) está reimplementada en dos capas distintas del sistema en vez de reutilizar la utilidad ya existente.**
- Ficheros: `PluginSchemaFieldNormalizer.php:21-40` (namespace `plugins\application`) vs `ExtensionPluginContentService.php:88-103` (`normalizeSchemaFields`, namespace `controllers`, casi el mismo algoritmo pero sin rellenar defaults de `type`/`required`/`label`). Es duplicación cross-capa: mismo problema resuelto dos veces con pequeñas divergencias, lo que es más peligroso que la duplicación exacta (puede divergir en comportamiento silenciosamente).

**9. Inconsistencia menor de patrón: `ConfigurationController::requestFactory()` no cachea la instancia, a diferencia de sus dos hermanos.**
- Fichero: `ConfigurationController.php:119-126`. `PluginManagerController.php:292-299` y `PluginExtensionController.php:399-406` asignan `$this->requestFactory = new RequestFactory(...)` antes de devolver; `ConfigurationController` construye una instancia nueva en cada llamada sin persistirla. Inofensivo en la práctica (la clase es stateless), pero es un ejemplo de copy-paste que diverge sutilmente entre tres controladores casi gemelos — típico de generación asistida sin unificar tras el hecho.

**10. `PluginRollbackService`/`PluginUpdateHistoryRepository` no purgan histórico — crecimiento no acotado de `plugin_update_history`.**
- No hay política de retención ni limpieza de snapshots antiguos; para un TFM/MVP es aceptable, pero conviene mencionarlo como deuda técnica reconocida en vez de omitirlo.

### NIT

**11. Demo plugin con "doble ping" redundante sin propósito.**
- Fichero: `plugins/demoinventory/Lifecycle.php:37-42,47-52`. `onUpdate()`/`onRollback()` llaman a `pingDatabase()` y luego, vía `touchUpdateContext()`/`touchRollbackContext()`, la vuelven a llamar si el contexto no está vacío — dos `SELECT 1` idénticos y sin efecto real, aparentemente solo para "tocar" el `$context` y que no quede como parámetro sin usar. Es artificial y no aporta nada como demo del hook.

## Valoración explícita: ¿están bien separadas las responsabilidades de los 10 ficheros de `plugins/application/`?

**Parcialmente.** Cinco de los seis servicios de ciclo de vida (`PluginStatusService`, `PluginSyncService`, `PluginUpdateService`, `PluginOutdatedService`, `PluginRollbackService`) tienen responsabilidad única y bien delimitada — cada uno hace una cosa (activar/desactivar; descubrir y registrar; aplicar update transaccional; calcular desfasados; hacer rollback transaccional) y `PluginAdministrationService` los orquesta correctamente como fachada para esas cinco operaciones (líneas 39-93 del fichero, delegación directa de una línea cada una).

El problema está en la **sexta responsabilidad, la de configuración**, donde el reparto es asimétrico e inconsistente:
- Para `entity`, toda la lógica de compilación de filas de configuración vive **dentro de** `PluginAdministrationService` (no en un servicio dedicado, a diferencia de las otras cinco responsabilidades).
- Para `extension`, sí existe un servicio dedicado (`ExtensionPluginConfigService`), pero no es autónomo: depende de que `PluginAdministrationService` le inyecte por closure su propia normalización de campos.
- `PluginSchemaFieldNormalizer` es una utilidad separada, correcta en su propósito, pero **su lógica se reimplementa además** en `ExtensionPluginContentService` (capa de controladores), en vez de reutilizarse.
- `InstalledPluginSchemaValidator` y `PluginSchemaMergeService` están bien extraídos como conceptos (validación de "¿es seguro aplicar este update?" vs. "aplica el merge"), pero comparten código de comparación duplicado en vez de un util común.

En resumen: no hay solapamiento funcional grave entre los seis servicios de ciclo de vida (esa parte del diseño es sólida), pero sí hay una **fachada que no es fachada** (`PluginAdministrationService` concentra más lógica de negocio que la mitad de los servicios "reales" que dice orquestar) y **tres focos de duplicación de utilidades** (comparación de tipo, comparación de esquema, normalización de campos) que deberían haberse unificado tras la ampliación de STORY 7.3 a extensiones, y no se hizo.

## Resumen de salud del subsistema

El núcleo transaccional de EPIC 7 (`update()` y `rollback()`) está bien diseñado y bien testeado: usa `version_compare()` estándar de PHP para semver (evita el clásico bug de reinventar el parser), envuelve la operación en una transacción real con snapshot previo en `plugin_update_history`, y los tests de integración verifican correctamente el rollback automático ante fallo del hook `onUpdate()`. Sin embargo, la ampliación funcional documentada en el backlog (STORY 7.3 "Refuerzo": soporte de configuración para plugins `extension`) no se propagó de forma coherente al resto del subsistema: el diff de actualización sigue siendo exclusivo de `entity` (el update de una `extension` es un no-op silencioso de schema), y la semántica de `custom_fields` diverge entre "catálogo de diseño" y "estado configurado" de forma que puede bloquear actualizaciones legítimas o activar campos sin consentimiento — el hallazgo más serio de esta auditoría. La disciplina transaccional, además, no es uniforme: solo `update()`/`rollback()` la tienen; `syncAll()` (alta de plugin) y `activate()/deactivate()` ejecutan efectos secundarios de lifecycle fuera de transacción. A nivel de mantenibilidad, `PluginAdministrationService` actúa como fachada para cinco servicios pero absorbe ella misma la lógica de configuración de entidades, generando el único solapamiento estructural relevante del subsistema. Ninguno de estos problemas es catastrófico para una defensa de TFM — el diseño general (contrato de plugin en capas, snapshot-based rollback, servicios de aplicación separados) es sólido y muestra buen criterio — pero conviene poder explicar con honestidad estos puntos si se preguntan en la defensa, especialmente la interacción entre configuración y actualización.

## Nota sobre cobertura de tests

La cobertura es buena en el "camino feliz" transaccional (altas, updates aditivos, updates no aditivos rechazados, esquema corrupto detectado, rollback exitoso y fallido, todo con aserciones directas contra la base de datos) y en el cableado HTTP de `PluginManagerController` (roles admin, códigos 404/409/422). Los huecos concretos detectados, todos ellos ligados a hallazgos de arriba: (a) ningún test de `PluginUpdateServiceTest.php` usa un fixture `type: 'extension'`, por lo que el hallazgo #2 es invisible a la suite; (b) ningún test guarda una configuración (`saveConfig`) y luego actualiza el mismo plugin, por lo que el hallazgo #1 (el más grave) tampoco está cubierto; (c) `CommentsPluginTest.php` nunca ejercita `PluginExtensionController::update()` (PUT), dejando sin probar tanto el hallazgo #3 como el comportamiento normal de edición; (d) no hay ningún test que simule un fallo de `onInstall()` durante `syncAll()` para verificar (o refutar) la atomicidad del alta, que es justo donde está el hallazgo #4. El test unitario `PluginSchemaMergeServiceTest.php` es correcto pero deliberadamente minimalista (tres casos), y no prueba la interacción con `plugin_suggested_custom_fields`.
